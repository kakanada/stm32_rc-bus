# rc_bus — приём каналов и телеметрия РУ (i-BUS / S.BUS / CRSF) для STM32

rc_bus — библиотека для STM32 F4/H7 из двух модулей: приём каналов
управления по FlySky i-BUS (примеры приёмников — FS-iA6A/FS-iA6B/FS-iA10),
Futaba S.BUS (пример — приёмники RadioMaster с S.BUS-выходом) или CRSF
(протокол TBS Crossfire / ExpressLRS, включая исходящую телеметрию батареи
приёмнику), и ответ телеметрией на опрос по отдельной шине датчиков i-BUS.
Работает поверх стандартного HAL UART/DMA, без bit-bang и без блокирующего
опроса в основном цикле.

## Возможности

- Три протокола каналов в одной библиотеке — `RCBUS_Config_t.protocol`
  выбирает i-BUS, S.BUS или CRSF для конкретного экземпляра (UART-линии);
  разные линии могут одновременно работать в разных протоколах.
- Любой из трёх протоколов работает и на обычной асинхронной линии (раздельные
  RX/TX, `HAL_UART_Init()`), и на аппаратной Half-Duplex/Single Wire
  (`HAL_HalfDuplex_Init()`) — без отдельного флага в `RCBUS_Config_t`: модуль
  только принимает, а приём (`HAL_UARTEx_ReceiveToIdle_DMA()`) не зависит от
  того, какой из двух режимов выбран в CubeMX, поэтому библиотека проверяет
  только параметры линии (скорость/биты/чётность/стопы), а не сам режим.
- Приём полностью аппаратный: DMA + определение простоя линии (IDLE) через
  `HAL_UARTEx_ReceiveToIdle_DMA()` — без опроса, без программных таймеров
  между байтами, без блокировок в основном цикле.
- Каналы нормализованы в единую шкалу "ширина импульса в мкс" (~988..2012,
  центр 1500) независимо от протокола — код приложения не меняется при
  переключении i-BUS ⇄ S.BUS ⇄ CRSF.
- Контроль целостности: контрольная сумма кадра (i-BUS, CRSF), явные биты
  frame-lost/failsafe (S.BUS) + таймаут по факту приёма валидного кадра
  каналов — единая функция `RCBUS_IsFrameLost()`/`RCBUS_IsFailsafe()` для
  всех трёх. Корректно принимает кадры каналов и от приёмников в режиме
  S.BUS2 (см. `sbus2_telemetry_signal`); на линии CRSF корректно пропускает
  (не как ошибку) прочие типы кадров приёмника, например LINK_STATISTICS.
- Восстановление после ошибок линии (framing/noise/overrun) — приём сам
  перезапускается, не "зависает" после первой же помехи.
- Телеметрия i-BUS: до `RCBUS_TELEMETRY_MAX_ADDRESS` (15) виртуальных
  датчиков на шину, неблокирующий приём опроса + неблокирующая передача
  ответа (`HAL_UART_Transmit_IT`) с корректным переключением направления на
  однопроводной half-duplex линии.
- Исходящая телеметрия CRSF: `RCBUS_CRSF_SendBatteryTelemetry()` неблокирующе
  отправляет приёмнику кадр "датчик батареи" (напряжение/ток/ёмкость/остаток
  заряда) — приёмник ретранслирует его по радиоканалу на экран пульта.
  Работает и на асинхронной, и на Half-Duplex линии (на последней — с
  корректным переключением направления, аналогично телеметрии i-BUS). Для
  остальных типов телеметрии CRSF (GPS, высотомер, ориентация, режим полёта
  и т.п.) — низкоуровневая `RCBUS_CRSF_SendFrame()` с произвольным payload,
  готовым к отправке любым известным `RCBUS_CRSF_FrameType_t`.
- Статические пулы экземпляров без malloc, идемпотентный `Init()`.
- Необязательная интеграция с **stm32_logger**: определите `RC_BUS_LOGGER_ENABLED`,
  чтобы ошибки инициализации, битые кадры и сбои UART отправлялись через
  `LOGGER_Log()`/`LOGGER_Mark()` (коды в `logger_codes.h`, `LOG_ADDR_RC_BUS`).
  Без этого define зависимости от `logger.h` нет вообще.

## Требования к настройке в CubeMX

Ниже — краткая сводка; подробное описание каждой настройки (что это, допустимый
диапазон, рекомендуемое значение и почему именно оно) — в [CUBEMX_SETUP.md](CUBEMX_SETUP.md).

Приём каналов (`rc_bus.h`):

| Протокол | Baud   | Данные        | Чётность | Стоп-биты | Сигнал        |
|----------|--------|---------------|----------|-----------|---------------|
| i-BUS    | 115200 | 8 бит         | нет      | 1         | прямой        |
| S.BUS    | 100000 | 9 бит (8+ч.)  | чётная   | 2         | **инверт.** ¹ |
| CRSF     | 420000 | 8 бит         | нет      | 1         | прямой        |

¹ S.BUS физически инвертирован. На H7 включается в CubeMX (UART Advanced
Init → Rx Pin Active Level Inversion); на F4 аппаратной инверсии в USART нет —
нужен внешний инвертор (например, простой транзисторный ключ) между линией
приёмника и ногой RX МК. Без этого S.BUS приниматься не будет. Если ваш
приёмник умеет и CRSF, и S.BUS (например, большинство ELRS-приёмников) — на
F4 проще и надёжнее выбрать CRSF: сигнал прямой, инвертор не нужен.

Для всех протоколов обязательно: DMA Rx в режиме **Normal** (не Circular),
USART global interrupt включён. Mode UART — на выбор, оба варианта
поддержаны одинаково для любого из трёх протоколов (`rc_bus.h` только
принимает, поэтому ему не важно, какой из них настроен):
- **Asynchronous** (обычный режим, раздельные RX/TX) — если у приёмника
  раздельные выходы каналов и телеметрии/ответа (или он вовсе не отвечает).
  Нога RX МК подключается к выходу приёмника, TX МК можно не подключать, если
  не собираетесь отправлять исходящую телеметрию CRSF
  (`RCBUS_CRSF_SendBatteryTelemetry()`) — для неё TX МК нужно подключить к
  соответствующему входу приёмника (обычно подписан отдельно от RX/выхода
  каналов).
- **Half-Duplex Selection** (Single Wire, `HAL_HalfDuplex_Init()` в MX-коде) —
  если у приёмника один общий провод на канал (типично для CRSF-приёмников
  с одним пином вместо раздельных RX/TX). **Провод приёмника подключается к
  ноге TX МК, а не RX** — в этом режиме периферия и передаёт, и принимает
  через один и тот же пин TX, нога RX не используется (это особенность самой
  периферии STM32, не библиотеки). `RCBUS_Init()` сам переводит линию в режим
  "только приём" (`HAL_HalfDuplex_EnableReceiver()` — сбрасывает `TE`,
  выставляет `RE`), чтобы собственный передатчик МК не держал линию в
  состоянии "mark" и не забивал сигнал приёмника — обратная телеметрия
  (i-BUS SENSOR — исключение, см. ниже) всё равно не отправляется, см.
  "Честные ограничения". CubeMX по умолчанию ставит для этого пина
  **GPIO Output Type = Open Drain** — это верно, но проверьте **Pull-up/
  Pull-down = Pull-up** (внутренний подтягивающий резистор МК): без него
  Open Drain не может сам поднять линию в "1", и при отсутствии внешнего
  pull-up на плате приёмника уровень на линии останется неопределённым.

Отдельно от настроек UART: если приёмник умеет несколько выходных протоколов
(например, PWM и CRSF/S.BUS одновременно на разных пинах) — серийный вывод
на нужном пине обычно нужно явно включить в настройках/конфигураторе самого
приёмника (Lua-скрипт на пульте, встроенный WiFi-конфигуратор и т.п.), иначе
на линии физически не будет ничего, кроме 0 В, независимо от настроек МК.

RCBUS_Init() проверяет только параметры линии (скорость/биты/чётность/стопы)
из таблицы выше — какой из двух Mode выбран, не проверяется и не влияет на
работу.

Для исходящей телеметрии CRSF (`RCBUS_CRSF_SendBatteryTelemetry()`) отдельный
DMA-канал на передачу не нужен — передача идёт через `HAL_UART_Transmit_IT()`
(прерывание, без DMA); "USART global interrupt", уже включённый для приёма,
обслуживает и её. Дополнительно нужен колбэк `RCBUS_UART_TxCpltCallback()` —
см. "Быстрый старт".

Телеметрия (`rc_bus_telemetry.h`) — отдельная физическая линия (не та же, что
приём каналов): Mode → **Half-Duplex Selection** (Single Wire), 115200 8N1,
DMA Rx Normal, USART global interrupt включён.

## Быстрый старт

### Приём каналов

```c
#include "rc_bus.h"

static RCBUS_Handle_t *rc;

void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    RCBUS_UART_RxEventCallback(huart, Size);
}

void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    RCBUS_UART_ErrorCallback(huart);
}

void AppInit(void)
{
    RCBUS_Config_t cfg = {
        .huart = &huart2,               /* уже проинициализирован CubeMX-ом под i-BUS/S.BUS */
        .protocol = RCBUS_PROTOCOL_IBUS, /* или RCBUS_PROTOCOL_SBUS/RCBUS_PROTOCOL_CRSF */
        .failsafe_timeout_ms = 0,        /* 0 = значение по умолчанию, 100 мс; для CRSF на
                                             высокой пакетной частоте (сотни Гц) можно поставить
                                             меньше, например 30-50, для более быстрой реакции
                                             на реальный обрыв связи */
    };
    rc = RCBUS_Init(&cfg);
}

void AppLoop(void)
{
    if (RCBUS_IsFailsafe(rc))
    {
        /* например, перевести приводы в безопасное положение */
        return;
    }
    uint16_t throttle = RCBUS_GetChannel(rc, 2); /* канал 3 (индекс с 0), ~988..2012 */
}
```

### Исходящая телеметрия CRSF (напряжение батареи приёмнику)

Дополнительно к колбэкам приёма каналов выше — если хотите отправлять
телеметрию, подключите ЕЩЁ и `HAL_UART_TxCpltCallback()`:

```c
void HAL_UART_TxCpltCallback(UART_HandleTypeDef *huart)
{
    RCBUS_UART_TxCpltCallback(huart);
}

void AppLoop(void)
{
    uint16_t battery_mv = 12600; /* например, из АЦП */
    RCBUS_CRSF_SendBatteryTelemetry(rc, battery_mv, 0, 0, 0); /* ток/ёмкость/остаток
                                                                   не отслеживаете - 0 */
}
```

Вызывайте не чаще нескольких раз в секунду — телеметрия делит канал с
приёмом каналов, слишком частые вызовы будут просто отклонены
(`HAL_ERROR`), пока не завершится предыдущая отправка.

Для остальных типов телеметрии CRSF (не "датчик батареи") — `RCBUS_CRSF_SendFrame()`:
вы сами собираете `payload` по официальной спецификации CRSF нужного типа,
библиотека только оборачивает его в кадр и отправляет:

```c
/* Пример: кадр ATTITUDE (0x1E) - тангаж/крен/рысканье, int16 big-endian каждый,
   единицы - радианы x 10000 (см. спецификацию CRSF); здесь просто нули. */
uint8_t attitude_payload[6] = { 0, 0, 0, 0, 0, 0 };
RCBUS_CRSF_SendFrame(rc, RCBUS_CRSF_FRAMETYPE_ATTITUDE, attitude_payload, sizeof(attitude_payload));
```

### Телеметрия (датчик на шине i-BUS)

```c
#include "rc_bus_telemetry.h"

static RCBUS_TelemetryHandle_t *tlm;

void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    RCBUS_TelemetryUART_RxEventCallback(huart, Size);
}
void HAL_UART_TxCpltCallback(UART_HandleTypeDef *huart)
{
    RCBUS_TelemetryUART_TxCpltCallback(huart);
}
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    RCBUS_TelemetryUART_ErrorCallback(huart);
}

void AppInit(void)
{
    RCBUS_TelemetryConfig_t cfg = { .huart = &huart3 }; /* Half-Duplex, 115200 8N1 */
    tlm = RCBUS_TelemetryInit(&cfg);
    RCBUS_TelemetryRegisterSensor(tlm, 1, RCBUS_IBUS_SENSOR_TYPE_VOLTAGE, 2);
}

void AppLoop(void)
{
    uint16_t battery_mv = 7400; /* например, из АЦП */
    RCBUS_TelemetrySetValue(tlm, 1, battery_mv);
}
```

## Честные ограничения

- Приём каналов (`rc_bus.h`) не разбирает телеметрию S.BUS2 (обмен в
  "слотах" между кадрами каналов) — у Futaba нет публичной спецификации
  этого обмена. Кадры каналов от приёмников в режиме S.BUS2 при этом
  принимаются корректно (см. `sbus2_telemetry_signal` — только детект факта
  сигнализации, не разбор данных).
- Телеметрия (`rc_bus_telemetry.h`) реализована только для i-BUS — у S.BUS
  нет отдельной шины датчиков, аналогичной i-BUS SENSOR.
- Каталог кодов типов датчиков телеметрии i-BUS не встроен (кроме
  `RCBUS_IBUS_SENSOR_TYPE_VOLTAGE`) — код типа передаётся сырым байтом,
  сверьтесь с таблицей вашего приложения передатчика.
- Требует HAL с `HAL_UARTEx_ReceiveToIdle_DMA()` — актуальные пакеты CubeF4 /
  CubeH7 его содержат; в очень старых пакетах HAL потребуется обновление.
- Программная инверсия сигнала S.BUS невозможна в принципе — периферия UART
  ищет старт-бит уже на инвертированном сигнале, поэтому инверсия только
  аппаратная (см. таблицу выше).
- Готовая функция-обёртка для исходящей телеметрии CRSF есть только для
  одного типа кадра — "датчик батареи" (`RCBUS_CRSF_SendBatteryTelemetry()`).
  Для остальных типов (GPS, высотомер, ориентация, режим полёта и т.п.)
  библиотека не знает формат payload — используйте низкоуровневую
  `RCBUS_CRSF_SendFrame()` и соберите payload сами по спецификации CRSF.
  Периодичность отправки — целиком на приложении, автоматической рассылки по
  таймеру в библиотеке нет.
- Прочие типы принимаемых кадров CRSF на линии (например, `LINK_STATISTICS`)
  корректно распознаются и игнорируются, не считаются ошибкой линии, но не
  разбираются — данные из них приложению недоступны.

Полный список функций и типов — см. [API_REFERENCE.md](API_REFERENCE.md).
